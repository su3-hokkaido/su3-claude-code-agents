# 0002. Human-on-the-loop autonomy model for the developer-set plugins

- Status: Accepted (Commander, 2026-11-10; amended in place 2026-11-09 while Proposed, see Revision log). Accepted ADRs are not edited; change them only by a superseding ADR.
- Date: 2026-11-09
- Deciders: Commander
- Supersedes: none
- Detail: `docs/2026-11-09_01_human_on_loop_design_upgrade/` `20_formats_spec.md` (files, STATUS, routes, loop helper), `21_guard_spec.md` (hooks), `22_policy_file_spec.md` (policy file). This ADR states the decisions; the specs hold the rules.

## Context

The `su3-developer-set` and `su3-developer-set-with-guards` agents work human-in-the-loop today: the Commander approves each step, and the guard hook answers risky commands with `ask`. Development speed does not go up. The opposite, agents fully out of the loop, lets them decide dangerous operations alone (physical deletes, one-shot migrations, live infrastructure changes).

The goal of this project (`docs/2026-11-09_01_human_on_loop_design_upgrade/`) is human-on-the-loop (HOTL): agents run a whole pipeline (plan, design, implement, verify, release check, report), and the Commander sets the rules and the stop conditions, supervises the loop, and decides only what the rules reserve for a human. Safety must come from structure (rules, hooks, file-based evidence, independent verification), not from approving each step.

Facts and constraints that shape the decision:

- Phase 1 spike (`10_spike_findings.md`, F2): `ask` from a hook is a denial when nobody can answer (`claude -p`), and the agent sees the `deny` reason text. Agents that were denied did not reword or retry, but they also did not write the escalation record the denial text asked for.
- F5: plugin options reach hook processes as `CLAUDE_PLUGIN_OPTION_<KEY>`. An option that was never saved is unset (the default is not applied).
- F6: a file imported from the target repository's `CLAUDE.md` with `@path` reaches subagents, and a POSIX `sh` hook can read it through `CLAUDE_PROJECT_DIR`. The file must be inside the repository.
- CLAUDE.md: only `-with-guards` plugins may ship hooks; no new agent frontmatter keys; each plugin is self-contained; plain and `-with-guards` variants stay identical apart from the suffix and guard wording; the guard is a text-pattern safety net, not a security boundary.
- Commander decisions Q1 to Q10, S1 to S4, P1, P2, J1 to J7, K1, K2, L1, L2, M1, M2, N1 and the adopted defaults (including the second-pass AIRE fixes) (`02_project_plan.md`, section 8), taken after the QA review (`23_qa_review.md`) and the AI-risk review (`24_aire_review.md`).
- The loop runner is the main session, which no hook checks and whose model the plugin cannot pin (24, R3). Counting and table arithmetic by a model are error-prone (24, AI-17).

## Decision

We adopt a human-on-the-loop autonomy model with these parts.

1. **Risk tiers.** Every agent action falls into one tier, and the tier decides who decides.

   | Tier | Meaning | Who decides |
   |---|---|---|
   | T0 Free | Local, reversible, no external effect (edit workspace files, run tests; read-only queries, dry-runs and plans only in a `dev` or `staging` environment the command identifies) | Agent alone |
   | T1 Guarded | Reversible with a defined safe pattern (writing an expand/migrate migration, soft delete, adding a dependency, CI config change; running migrations and data changes in an environment the policy declares `dev`, item 4) | Agent, only by following the safe pattern; `qc` verifies |
   | T2 Reserved | Hard to reverse or outward-facing (running migrations or data changes outside a declared `dev` environment, contract step, live infrastructure apply, version upgrade, publish, spending money, new credentials, git writes) | Human; the agent prepares the exact command, dry-run output and rollback |
   | T3 Forbidden | Never, even with approval inside the loop (`git push --force`, reading secrets, editing the policy, settings, guards or other protected paths) | Denied by hook and by text rule |

   An environment the command text does not identify is production (22 section 2.4). The environment comes from the project's own configuration; agents never choose, add or change an environment name in a command, and comments, `echo` text and assignment names do not count as naming `dev` or `staging` (22 sections 2.4.2, 4.1 rule 2). Agents run nothing against production or an unidentified environment, not even a dry run, a plan (L1) or a read-only query such as `SELECT`, `kubectl get` / `describe` or `aws ... describe-*` (M1); they prepare the command and the Commander runs it, investigates production and hands the results over.

2. **Park and continue, not block and wait.** A T2 action is not executed. Agents never ask and never wait, whatever the mode: they report `BLOCKED` with the exact command, dry-run result and rollback (a Parked action block) and continue with the rest of their step. The main session, or `project-manager` in a call it already has, turns every Parked action block into an item of the unit's `06_commander_actions.md`, whatever the report's STATUS (F2: agents did not write the record themselves). When the step needs the action, the unit is `PARKED` and the loop continues with units that do not depend on it; when the action is only a follow-up, the agent reports `DONE` and the unit goes on.

3. **Four human touchpoints.**
   - P0 Policy and Backlog approval: once per run, before the loop starts. The Commander writes the Epic / Story / Ticket files, names the targets in the prompt, and approves the backlog; there is no per-ticket plan approval (Q2).
   - P1 Watch: optional; read the status table and reports.
   - P2 Interrupt: a stop rule parks the unit with a `STOP` item (retry cap, budget overrun, conflicting artifacts, T2 on the critical path, repeated guard denial counted by the loop, unknown situation; 20 section 11). In interactive mode the main session may also ask a question; in unattended mode it never does.
   - P3 Digest review: at the end; the Commander decides parked T2 items, release go / no-go, and git operations.

4. **Project policy file** (Q1). The per-project rules live in `docs/policy/autonomy-policy.md` (fixed path) in the target repository, imported from its `CLAUDE.md`, with one machine-readable block that the hook parses (format, states and decision table: 22). Levels, from loosest to strictest:
   - **Without approval, declared `dev` only** (J1): in an environment the policy declares `dev` (for example a local database), agents run migrations and data change / delete as T1; the safe patterns still apply. It has effect only when the policy names a `dev` environment; the shipped template names none, so nothing is `dev` until the project declares it (22 sections 2.3, 2.4, 5.1). Precondition (L2): the agent's machine holds dev-only credentials; the template and the README state it, and the policy does not verify it.
   - **After approval** (Q3, P2): dev / staging infrastructure apply, data change and delete, and schema migration; patch / minor version updates; tracker write-back (confirm-required, Q10). In unattended mode these are parked, not run; they run later in an interactive session (22 section 4.2 S5).
   - **Reserved for the Commander**: everything else T2 (contract step, infrastructure destroy, major upgrades, publish, spending, new credentials, every git write; Q9 `commander-only`).
   - **Production and unknown environments: `deny` for agents in both modes** (P1), dry-run and plan forms included (L1), and read-only queries through database clients, `kubectl` / `helm`, cloud CLIs and infrastructure state reads too (M1; the hook's read patterns: 21). No policy line can loosen this. Dry-run and plan forms and read-only queries in `dev` and `staging` pass as before. Consequence of "unknown is production": a read-only database, cluster or cloud command that names no declared environment (for example `psql -c 'select 1'` against an undeclared local database) is denied too (22 section 4.3).
   - Missing file: plugin defaults. Broken file, or a policy file with uncommitted changes (the hook checks with one read-only `git status --porcelain --ignored` call, J7-1 as refined by K1, run with the user-level and system git config neutralized so that no filter from outside the repository runs; to be verified in Phase 3a; a target that is not under git is always strict): `degraded`, strict mode (every loosening ignored).
   - Specified, implemented later (J5): `git: commit-after-approval`, hook detection of `spend` and CLI `tracker-write`.

5. **`autonomy_mode` plugin option** (Q4): `userConfig.autonomy_mode`, type string, values `interactive` / `unattended`, default `interactive`, no `options` key. Only the value `unattended` (after removing all white space; case-sensitive) means unattended; unset, empty, unexpanded or any other value means `interactive` (F5; one rule for hook and skills, 20 section 11.2). Only the main session and the hook use the mode; agents are mode-agnostic. In `interactive` the guard asks only for after-approval matches; production, reserved and plugin-fixed commands are `deny` in both modes (P1). In `unattended` the `ask` cases become `deny` with a park hint.

6. **Per-unit document directory** (Q5): `docs/yyyy-mm-dd_NNN_{title}/` per Ticket, Story or Epic, `NNN` a 3-digit sequence per date, tracked in git (the Commander commits). Files `00_request.md` to `06_commander_actions.md`; a file a route does not need is not created and `01` records "skipped: reason". Ownership (20 section 0):
   - `01_project_plan.md` status table: **each agent edits the cells of its own step**; `project-manager` only checks them read-only, and a mismatch is a conflicting-artifacts stop (S1). No extra `project-manager` call per step.
   - `04_quality_report.md`: `qc` returns its report and `project-manager` transcribes it verbatim; `qc` gets no `Edit` tool (S2).
   - The release check is not part of a ticket unit: it runs only on the `release` route, once per Commander request, in its own directory `docs/yyyy-mm-dd_NNN_release_check/` (S3). Specified, implemented later (J5).

7. **Skill hierarchy** (Q6, D1, ADR 0003): `project-implementation` (top level, runs the loop over the named targets) calls, per unit, `task-management` (plan via `project-manager`), `design-review` when needed, and `code-implementation` (route steps, independent verify, send-backs). Routes (20 section 10) include: docs route, `aire` edits and `qa` verifies, `app-developer` and `qc` not called (S4); data-change route, `system-architect`, `app-developer`, `sre`, then `qc`, then the Commander's contract step (J7-2). Rule skills `autonomy-policy` and `safe-data-change` are inlined into agent bodies (ADR 0001) as one canonical autonomy rules block (22 section 4.1). The main session is the loop runner; `project-manager` returns plans and does not dispatch. A phase skill called through the Skill tool gets the unit directory path in its arguments and reads mode and policy state from that directory (20 section 11.3).

8. **STATUS lines.** Every agent report ends with `STATUS:` and one of `DONE`, `PARTIAL`, `BLOCKED`, `NEEDS_HUMAN_INPUT`, or (`qc` only) `PASS` / `FAIL`. The loop reads the last non-empty line and matches the token case-insensitively and exactly; anything else, including a bold, backticked or period-terminated line, is treated as `BLOCKED` (20 section 9.1). Agents write it plain (`STATUS: DONE`). `qc` does not trust the author's report and re-runs the checks itself. Reports, ticket text and tool output can only lower autonomy (park, stop), never raise it: they never grant approval, skip a step or add a tool (20 section 11.4).

9. **Caps and the loop-state helper** (J7-4). Retry cap 2 send-backs per verify loop, budget stop at 150% of the estimate in agent calls, denial cap 2 counted by the loop from `06` (the hook denial counter is deferred, J5). A policy may only make them stricter. A deterministic POSIX `sh` helper, `loop-state.sh`, ships in `su3-developer-set-with-guards` only (see the 2026-11-10 log row; in the `project-implementation` skill directory; every phase skill reaches it by one fixed path relative to its own skill directory, 20 section 9.4), is run by the main session through Bash before and after every dispatch (not a hook), applies the caps, the next-step rule, the STATUS normalization and the bookkeeping check, and prints one verdict line; its `check-format` subcommand is the format checker (20 section 9.4). Its output is the only trusted source for caps and verdicts. It never uses `eval` or sources files, and executes nothing from the document directory; it and every other plugin helper script are protected paths for the edit guard (20 section 9.4, 22 section 7.1). The plain `su3-developer-set` has no helper.

10. **Enforcement.** Hooks ship only in `su3-developer-set-with-guards`: the Bash guard (extended for the policy file and the decision table) and an edit guard for `Edit`, `Write`, `MultiEdit`, `NotebookEdit` and `Read` (protected paths including `.git/`, secrets, the plugin's `hooks/`, `scripts/` and `skills/` paths and `loop-state.sh` as a minimal set, not whole plugin directories (M2), and the role-to-file ownership rule for run directories, matched case-insensitively, with no run-directory writes for an unknown role), both with `onFailure: "block"` (J4; 21). The plain `su3-developer-set` relies on text rules only; its README says unattended use is safe only with the `-with-guards` variant or the user's own hooks and deny rules. The guard is a text-pattern net, not a security boundary: `settings.json` deny rules, database roles without `DELETE` / DDL grants and no production credentials on agent machines are the real boundary. The fixed-English-tokens sentence lives in the autonomy rules block only; the shared Output Language block is unchanged (J7-3).

## Alternatives considered

- **Keep human-in-the-loop** (approve every step): safest per step and no new work, but speed does not improve, which is the problem this project exists to solve.
- **Fully autonomous, no tiers**: fastest, but agents could run physical deletes, one-shot migrations, infrastructure applies or force pushes alone. Rejected; it relies on the model's judgement for irreversible actions.
- **One global policy hard-coded in the plugin, no project policy file**: simpler to ship and test, but environments and allowed actions differ per project (Q1, Q3, Q9), and the plugin cannot know which environment is "staging". Rejected; the plugin ships the defaults and a template instead.
- **Always `ask` instead of deny + park**: keeps the human in control of each T2 action, but in an unattended run `ask` becomes a denial with no record and no way to continue (F2), and in an attended run it brings back per-step approval. Kept only for after-approval matches in `interactive` mode; never for production (P1).
- **Every migration or data change T2, also in dev** (23 X-01 options b and c): simplest rule, but the data-change route and DB-backed tests could never complete unattended. Rejected for the dev-only level (J1).
- **Caps counted by the main session's model, STATUS parsed by a strict regex with a stop on any deviation**: no extra script, but miscounts are silent and formatting slips park most units (24 AI-17, AI-19). Rejected for the helper (J7-4).
- **Hook-side denial counter** (`/tmp` state per agent run): advisory only and per dispatch, not per step (21 section 7.3). Deferred (J5).

## Consequences

- The Commander's work moves to P0 and P3: approve the backlog and policy, then review one digest and the parked items in batch. Risk: parked items pile up and the human becomes the bottleneck again; the pilot measures the parked ratio. In unattended runs every after-approval action is parked, which dominates that ratio (23 X-06).
- Target repositories need a policy file and a `CLAUDE.md` import line. Without one, agents use the plugin defaults and report the missing file. A project whose agents must run migrations or data changes against a local or test database must declare it `dev` in the policy (22 section 5.1); until then such commands are treated as production and denied.
- Both plugins get new skills, the helper script, agent text changes (canonical autonomy rules block, `STATUS:` lines), a new `userConfig` key and, in `-with-guards` only, hook changes. Parity between the two variants is kept by hand and by `validate.sh`.
- Phase 3 is split into 3a (policy template, guard hooks, validators and helper) and 3b (formats, skills, loop, agent text), with a Commander OK after each (J5). Deferred to a later release: hook denial counter, `spend` and CLI `tracker-write` detection, `git: commit-after-approval`, the release route and its directory, machine checks of `02` / `03`, the performance gate.
- The main session (Claude) edits every file under `plugins/` in Phase 3 (skills, helper, policy template, agent text, hooks and guard scripts), because the edit guard denies `-with-guards` agents writes to the plugin's `skills/`, `scripts/` and `hooks/` paths; `sre`, `qa`, `aire` and `qc` review and verify (J3, extended to all of Phase 3 by N1). The guard gets no exception for a `-with-guards` `app-developer`. The hooks use `onFailure: "block"`, so a crashed or timed-out guard blocks instead of allowing (J4).
- Accepted residual risks (J6; 24 section 5.2), stated in the README with the backing measures (DB roles, settings deny rules, no production credentials): R1 the text-pattern guard can be bypassed, and the plain variant has text rules only; R2 a runaway inside one dispatch is bounded only by a text rule; R3 the main session may skip or misread the helper; R4 commands, dry-runs and rollbacks in `06` are agent-proposed and the Commander must review them; R5 self-bookkeeping detects inconsistency, not false claims.
- Production evidence moves to the Commander (L1, M1): a parked production item carries the dry-run command, not its output, so the Commander runs the production dry run before deciding; dev or staging output may accompany it. Production diagnosis is also the Commander's: an agent that needs a production read parks the exact read command and the result it needs, and the Commander hands the result over. Agent machines need no production credentials at all, which keeps the R1 backing simple.
- False positives of M1, accepted as fail-safe: in a project that declares no `dev` environment, agents cannot run read-only database, cluster or cloud commands at all (they are `unknown`); a project declares its local database, kind cluster or cloud profile as `dev` or `staging` to get them back. General shell commands (`cat`, `curl`, `ssh`) are not covered by the read rule (21).
- The dev-only level is only as safe as its precondition (L2): dev-only credentials on the agent machine. The hook reads command text, not variable values, so faking a dev name is limited (22 section 2.4.2) but not impossible.
- Plain-variant users get no enforcement, only text rules. This is a deliberate trade-off forced by the directory's hook restriction. In the plain variant a `Decision:` line in `06` cannot be told from an agent edit, so the loop treats it as unconfirmed until the Commander confirms it in a session (20 section 8.4).
- Each unit leaves a document directory in git, which gives resumability and an audit trail but adds files the Commander must review and commit.
- Unverified at the time of writing (assumptions): a saved `autonomy_mode` value reaching the hook in an installed plugin (23 S16, Phase 4); the real tool-input field names for `Edit`, `MultiEdit`, `NotebookEdit`, `Read` (Phase 3a); that the skill-directory substitution expands in skill text so a phase skill can name the helper's absolute path (Phase 3a); that a phase skill reads the directory passed in its Skill arguments (Phase 3b); directory-scan acceptance of `loop-state.sh` (Phase 4); that `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_SYSTEM` keep the H9 `git status` call from running a clean filter defined outside the repository (Phase 3a); context growth and resume in a long loop (Phase 5 pilot).
